# Rendering

Rendering is per route. A route reading content follows `getContentRender()`, which follows the `mode` of its content source, and a route derived from a route follows that route.

# Astro runtime

`packages/astro` (`@fumapress/astro`) runs the site of `press.config.tsx` on Astro, on top of the low-level `@fumadocs/astro` integration.

- Bind the concepts of `@fumapress/core` (routes, middleware, head, slots, `build`) to Astro. Never add Astro hooks to plugins: they receive the core `Context`, and a feature that needs a new hook belongs in core.
- Overrides go through existing concepts: components by name in the MDX components module, `ui.renderPage` returning an `.astro` layout with a `createIsland()` root, `ui.providerProps` of the site, the search plugin, and users' own Astro routes. Rejected before, don't reintroduce: per-plugin layout exports, page or layout modules, a `searchEngine` field, `oauth`/`proxy` plugin options, plugins with their own blog or changelog UI.
- Every page Fumapress renders is one press island (`src/island`) unless `ui.renderPage` returns an `.astro` layout: the result of `ui.renderPage` (or the built-in UI of `renderDefault`) in the root provider. An `.astro` layout renders instead of it, with its `createIsland()` root as the press island and the page content in an island of its slot. Client components (`'use client'`) and MDX components hydrate, other components render on the server. Props of hydrating components must be serializable: devalue values, elements and client components. A client component with a function prop throws, an MDX component with one renders on the server. The page tree of a language goes by identity to its file, collection bodies are Astro slots.
- Modules reachable from compiled MDX (the components modules, `ui/content.tsx`, `ui/link.tsx`) never import the runtime or the layout module. Compiled MDX in a cycle with the source makes Astro's build superlinear.
- Injected routes and the middleware are real files in `dist`. Modules imported only by `.astro` files or generated code are tsdown entries, otherwise unbundling drops their exports.
- Search plugins give the root provider their dialog in `providerProps({ lang })`: `search: { SearchDialog, options }`, a `'use client'` export on the provider hook of `fumadocs-core/search/client` (`from` for a static index, `api` otherwise, `locale` of the page), shared with Waku. A custom dialog is `ui.providerProps.search.SearchDialog` on the same hook and receives the plugin's `options`, never a `SearchClient`.
- The `build` of plugins runs on the pages of Astro's default prerenderer, in the build process. Other prerenderers fail with the reason.
- Check changes across setups: `base` with `trailingSlash` and `build.format`, static output, an adapter and `output: 'server'`, a dynamic source, i18n with every `hideLocale`, a custom `ui.renderPage`, custom search, own pages with `HomeLayout.astro`.
- Astro needs Node >= 22.23.4.

# Vue runtime

`packages/vue` (`@fumapress/vue`) is Fumapress for Vue, on Vite and Nitro. It doesn't use `@fumapress/core`, and a site installs neither Fumadocs nor React: tsdown bundles the parts of Fumadocs it uses, and `react` resolves to a shim (`tsdown.config.ts`).

- A site installs little: every dependency is weighed by what it adds to `node_modules`. What the package can bundle is a devDependency bundled into `dist` (Reka UI, the Markdown parser of search results, `yaml`, the typography plugin); what only some sites use is an optional peer; the stylesheets are compiled at build time (`scripts/build-css.mjs`), and the icons and the entries of Reka UI are generated by hand and committed (`scripts/gen-icons.mjs`, `scripts/gen-reka.mjs`). Dependencies are at their latest version, and none is deprecated: check with `pnpm --dir packages/vue outdated`. TypeScript stays at 6 in this package: `vue-tsc` needs its JS API, which 7 doesn't have.
- The router is `src/router.ts`, not Vue Router: custom pages by their path, and one route for everything else. Custom pages and the routes of plugins share one path syntax (`[name]`, `[...name]`) and one matcher. The more specific page renders a URL: a custom page at a fixed path, then a content page or a view, then a custom page with params. The app loads pages and updates the head with `router.beforeEach` and `router.afterEach`, the hooks a site adds in `enhanceApp`, then `router.start()` loads the first page: no other way to act on a navigation.
- A file or folder whose name starts with `_` is not a page, in `src/pages` and in collections (`isHidden` of `src/vite/scan.ts`, `HIDDEN` of `src/vite/macro.ts`): it holds what pages import.
- Collections are the macros of `@fumapress/vue/content` in `press.config.*`, with the call shape and static rules of `fumadocs-mdx/macro`: `defineDocs()` and `defineCollections()` initialize a top-level `const`, with literals for `dir`, `files`, `type` and `lastModified`. The Vite plugin compiles a call to `await defineDocs(options, files)`, where `files` are `import.meta.glob` imports of the folder (the frontmatter of each page as its own module, the compiled pages, their files in the browser build, the `meta.json` files) and the dates of one `git log` with `lastModified: true`. The options stay in the module, and the server validates every file with their schemas (a Standard Schema, or the built-in one with the fields of Fumadocs' schemas) when the collection is created. The config module is never run in the build: the plugin reads the same calls statically for the entries of the browser build, and a site without `press.config` gets a generated one that is compiled the same way. Compile options are global (`press({ markdown })`), not per collection. A collection is only its source (`toFumadocsSource()`); `baseDir` is the URL prefix of any source, applied by the context.
- A path has one form inside the site: decoded, with single slashes, without a trailing one. A URL is decoded once where it comes in (`decodePath`) and encoded once where it goes out (`encodePath`): never decode or encode in between.
- A site writes paths without the base path, and the site adds it where the path goes out: links in the router, the images and `src` of content when a page is compiled (a file next to the page is imported instead), and the `href` and `src` of the head tags of the config and the theme.
- The stylesheet of a site is compiled: `dist/style/<color>.css`, built from `css/` by `scripts/build-css.mjs`, so a site needs no Tailwind CSS. A site that wants Tailwind CSS adds its Vite plugin and writes `src/theme.css` from the sources of `css/`.
- The server a build prerenders with is told apart by `import.meta.prerender`, which Nitro sets at build time, never by a request: only it lists the paths to generate, runs `build` hooks and writes `404.html`.

- `src/` is built to `dist/`: the config, content, server, client and the Vite plugin. `runtime/`, `ui/` and `theme/` ship as source and are compiled by the site's Vite, since they import `.vue` files and the virtual modules of the plugin.
- Plugin hooks keep the names and signatures of `@fumapress/core`, so server-side plugins port across runtimes.
- The builder is core's, typed by the content: `createPress(content, options)` infers the site's `AppShape` from the `Source` types of Fumadocs, then `.plugins()`, `.views()` and `.config()` are typed by it, and a page has `type`, the key of its source. Port core's types (`Plugin<C, T>`, `Declared`, `MergedTypes`, the unknown key check), and differ only where the port has no React (a view carries props, not a node) or where a site without `i18n` still has a language (`lang` is `string`). Other files read the site's types with a type-only import: `PageOf<typeof app, K>`, `PressContext<typeof app>`. `test/types.test.ts` checks them in the declarations of the build.
- What the server sends to the browser (layout props, the page tree) is serializable. UI is changed in the theme module, never by config functions that return elements.
- The app reads the server through data routes (`createApi({ data })`, `load(path)`): the page, the site data, the search index. A feature that needs data in the browser adds a data route, not a new channel.
- A page is content or a view, and what the browser receives for it is `PageOf<A, K>`, with core's names: a content page has `type` (its source key), `url`, `data` (the validated frontmatter, as JSON), `pageData` (`getPageData()`), `toc` and `Content`; a view has `type`, `url`, `props` (as JSON) and `pageData`. The server renders with the same JSON (`toJson` of the context), and sends nothing else of `page.data`. The body of a content page is a compiled module, HTML, or a view (`props` in place of `Content`, for a source a plugin declares in `pages`). `.views()` makes the site's own pages outside the content, a builder stage since they are what the site consists of, not a feature; its names are not source keys or names of plugin views. `createView` makes those of plugins, with the view types they declare. Don't add another way for plugins to render UI.
- A site has languages, one without `i18n` (`site.lang`). What depends on the language is keyed by it: the site data and the search index have one data route per language, `layoutProps` receives `lang`, views exist per language, and `ui.translations` is the translations API of `@fumapress/vue/i18n`, checked against the languages. The app holds the data of one language, the one of the document (`<html lang>`): a link to another language loads a new document. `hideLocale: "always"` is refused, since languages are told apart by their URL.
- A theme (`defineTheme<typeof app>()` of `@fumapress/vue/theme`) has `extends`, `Root`, `NotFound`, `views`, `components`, `icons`, `head` and `enhanceApp`. It is used as written: it builds on another theme only through `extends` (maps merge with its entries winning, `head` lists join, every `enhanceApp` runs, `Root` and `NotFound` are replaced; `resolveTheme` of `src/client.ts`), and the Vite plugin never merges themes. `views` gives each page type its component (a source key, a view name, or `default` for content types without one), which receives one prop, `page`; a value is a component or a function importing it, which `loadPage` awaits with the page. `PageView` renders it, or `NotFound`. The types check the keys, the `page` of each component (contravariantly, through `setup` or a functional component), and that the theme's own `views` has a component for every type only a component of its own renders (a view, a source a plugin renders as views), as required keys, so the error names the type; a theme takes the components of another by spreading its `views`. A content type has its own component or `default`, here or in `extends`: the server checks it when the site starts (`createFetchHandler({ views })`).
- A theme is not a layout. A layout is a component of `views` for content pages, imported by the theme: `theme/layouts/<Name>.vue`, exported as `@fumapress/vue/theme/layouts/<name>` (`docs`, `notebook`, `glass`, `spacious`, `flux`). It takes `page`, and `layoutProps` and `pageProps` typed by its layout of `ui/layouts`, which can hold components and win over `ui.layoutProps` of the config (core's `renderDefault` options, with `mergeOptions`). A layout component is a generic SFC (`generic="Page extends ContentPage"`), so vue-tsc types it as a function and it fits any content type in `views`. `@fumapress/vue/theme/layouts/home` is the home layout around a slot, for landing pages, views and custom pages. The config has only the props every layout shares (`ui.layoutProps`, `LayoutProps` of `src/core/layouts.ts`), never the choice of a layout.
- `theme/` is a thin wiring of `ui/`. `@fumapress/vue/theme` (`theme/index.ts`) exports `defineTheme` and `baseTheme` (`theme/base.ts`: `Root`, the lazy `NotFound`, the Markdown components, no views); `@fumapress/vue/theme/default` is the base theme with the docs layout as `views.default`. A site with another layout extends the base theme, so the code of the docs layout is in none of its files. The barrel exports nothing a page doesn't need (no `NotFound`, no layout): a re-export puts its module in the entry chunk. Since layouts are static imports of the theme, the JS of a page is that of the layout its theme imports, and a site that doesn't import the flux layout needs no `motion-v`. What only some pages use is lazy (the not found page, components like `Accordion`), and a theme's `views` should be (a function importing the component).
- A page shows once its data, its content and the component of `views` have loaded (`loadPage`), so a navigation never shows a page before its component.
- A site needs no TypeScript: the Vue compiler reads the types of props from the file system, and finds a type imported from a package through Node (`typeResolver` of the Vite plugin) when the site has no TypeScript with a JS API. So a type a `.vue` file passes to `defineProps` or `defineEmits` is declared in this package, and a type of another package (like `HTMLAttributes` of `vue`) is behind `/* @vue-ignore */`. `node packages/vue/scripts/check-sfc.mjs` compiles every component that way.
- `packages/vue-cli` (`@fumapress/vue-cli`, the `fumapress-vue` command) copies a module of `ui/`, or `theme/`, into a project. A copy of the theme is the theme module of the site: `default.ts` is its `index.ts`, the API of `theme/index.ts` stays in the package, and of `theme/layouts` it has the layouts its files or the project import, which the copies then import in place of the package's. A copy imports the rest of the UI from the package by name, and the copies of the project by path. So a module of `ui/` imports another one by its folder, never a file inside it: the test of the CLI copies every module to check.
- Run commands with Node 24. Check a change with `pnpm --dir packages/vue build`, `test` and `types:check`, then `pnpm --dir examples/vue build`.

## UI port

`packages/vue/ui` is a port of Fumadocs UI to Vue: the source is `packages/base-ui/src` of the Fumadocs repository. It stays a port, so that changes of Fumadocs UI can be followed file by file.

- Paths mirror the source. `src/<path>/<name>.tsx` is the folder `ui/<path>/<name>/`: one `.vue` file per exported component, named after the export, and an `index.ts` that exports the same names (components, composables, types, helpers). Import a module by its folder: `@fumapress/vue/ui/components/tabs`.
- The DOM, class names, ids, `data-*` and `aria-*` attributes, texts and behavior are those of the source. Copy Tailwind classes as they are. Don't restyle, rename, reorder, simplify or add features, and don't leave out a branch of the source.
- Base UI primitives become Reka UI ones, bundled by family into `dist/reka`: import a primitive from `reka-ui` and run `node packages/vue/scripts/gen-reka.mjs`, which adds its family and rewrites the import to `@fumapress/vue/reka/<family>`. A site never installs Reka UI. Their state attributes differ (`data-open` on Base UI, `data-[state=open]` on Reka), so translate those selectors: `packages/radix-ui/src` of Fumadocs has the same files written for Radix, whose attributes are Reka's.
- Props keep their names and defaults. `children` is the default slot, a prop taking a node or a render function is a slot of the same name, `onXChange` with its value is `v-model:x`, and another `onX` is the emit `x`. A hook is a composable of the same name, and a context is `provide`/`inject` with a typed key in the same module: `Symbol.for("fd-<name>")` with a name no other module uses, so a copy of the module in a project and the one of the package share the context.
- The React modules of `fumadocs-core` have Vue ports under `ui/core/` at the same path (`fumadocs-core/link` is `ui/core/link`). Icons keep their Lucide names and come from `ui/icons`, generated from `@lucide/vue`: import an icon as the source does and run `node packages/vue/scripts/gen-icons.mjs`, which adds it and rewrites the import. A site never installs the icon set. `cn` is `ui/utils/cn`.
- Code runs on the server too: browser APIs only in `onMounted` and event handlers. A module has no side effect at its top level (`sideEffects` of `package.json`), so a page only loads what it renders: a stylesheet is imported by the component that needs it, not by an `index.ts`. `v-html` only where the source has `dangerouslySetInnerHTML`.
- `index.ts` has the public names of the source module. State that several `.vue` files of a module share, like injection keys, is in a sibling `context.ts`, so a `.vue` file never imports a value from its own `index.ts`. Composables return refs, and a context is an object of refs.
- Class strings are in `<script setup>` or a static `class="…"`, not inside a quoted `:class` expression, where the port check misses them. A template has no comment at its root.
- UI files import the built entries by package name (`@fumapress/vue/client`, `@fumapress/vue/page-tree`) and other UI modules by relative folder. They never import `fumadocs-core`.
- Not ported: `og*`, `provider/*` except `base`, `*.rsc.tsx` and `mdx.server`. No dependency beyond those of `package.json`. Optional peers, installed by the sites that use them: `motion-v` (the Flux layout), `algoliasearch` and `@orama/core` (their search dialogs, which only import types).
- Where the source depends on a React library without a Vue version, the part it uses is ported into the module: `react-medium-image-zoom` in `components/image-zoom`. The dynamic code block highlights with `@fumapress/vue/highlight` (Highlights), not Shiki.
- A Base UI primitive Reka UI lacks is ported to `ui/primitives/<name>`, with the attributes of Base UI, so the selectors of its users stay as in the source: the drawer of the Glass layout. Otherwise it is translated to the closest Reka primitive with the same DOM (the menus of the Spacious layout).
- A value that is a React node in the source's data (an icon of the page tree, of a link item or of a tab) is `string | Component` here, rendered with `RenderNode` of `layouts/shared`.
- `node packages/vue/scripts/check-port.mjs <source.tsx> <ported folder>` lists the classes a port lost or added. Lost classes are bugs unless they are state selectors translated for Reka.

# Release workflow

This repository uses [Tegami](https://tegami.fuma-nama.dev) for versioning and publishing.

## Write changelog files

Create pending changelog files under `.tegami/` as `YYYY-MM-DD-{hash}.md`.

See the [changelog format docs](https://tegami.fuma-nama.dev/changelog) for details.

### Example

```md
---
packages:
  "npm:@acme/ui": patch
---

### Fix button hover state

The hover color now matches the design system.
```

### Package references

Use package names, ids, or groups in frontmatter. For example:

- `"@acme/ui"` — package name
- `"npm:@acme/ui"` — package id
- `"group:acme"` — every package in a group

Rules:

- Include YAML frontmatter with `packages`
- Include at least one `#`, `##`, or `###` heading in the body
- Write user-facing release notes under each heading
- Do not edit `.tegami/publish-plan` or package `CHANGELOG.md` files directly
