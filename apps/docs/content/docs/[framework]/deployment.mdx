<show when={props.framework === "waku"}>

`fumapress build` writes the site to `dist/`. Deploy to a platform if anything renders on demand, or to a static host if nothing does.

</show>

<show when={props.framework === "astro"}>

`astro build` writes the site to `dist/`. Without an adapter, the whole site is static, so [deploy it](https://docs.astro.build/en/guides/deploy) to any static host. With an adapter, your `output` and `prerender` settings work as they do in Astro.

</show>

Pages of a static source are prerendered. Pages of a dynamic source, like [Notion](./content-sources/notion.mdx), render on demand, and one site can mix both. Files generated from your content, like `.md` files, the sitemap and Open Graph images, use the same render mode as their pages.

## What Needs a Server

<show when={props.framework === "astro"}>

Without an [adapter](#adapters), the build fails on anything in this list and prints the reason.

</show>

- A dynamic source, like [Notion](./content-sources/notion.mdx) and [Sanity](./content-sources/sanity.mdx).
- [AI chat](./plugins/ai.mdx#ai-chat) and [MCP](./plugins/ai.mdx#mcp).
- The [OpenAPI proxy](./plugins/api-docs.mdx#proxy).
- [Feedback](./plugins/feedback.mdx) with actions on the server. Actions in the browser don't need a server.
- [Server-side search](./search.mdx#server-side-search), when you enable it.
- Custom pages and API routes rendered on demand.

<show when={props.framework === "waku"}>

[Self-hosted image optimization](./content.mdx#image-optimization) and the `middleware` of a plugin that you list in `.plugins()`, like [authentication](./authentication.mdx), need one too. A build without a server warns about that middleware.

The default plugins don't need a server. On a static build, they leave out what needs one, like the Markdown [content negotiation](./plugins/ai.mdx#content-negotiation) of llms.txt.

</show>

<show when={props.framework === "astro"}>

A plugin with `middleware` doesn't fail the build. Without an adapter, the build warns that its middleware never runs.

</show>

## Render Mode

The `mode` option of `createPress()` changes when content renders, for every source or by source key:

```tsx title="press.config.tsx"
createPress(
  {
    docs: docsSource,
    guides: notion.dynamicSource({ baseDir: "guides" }),
  },
  { mode: { guides: "force-static" } },
);
```

- `auto`: the default described above.
- `force-dynamic`: render on demand, so that every request reaches middleware, like for [authentication](./authentication.mdx).
- `force-static`: load a dynamic source once at build time, and prerender its pages.

<show when={props.framework === "astro"}>

With `output: "server"`, `auto` renders every source on demand, like other Astro routes. To build a dynamic source without an adapter, set `mode: "force-static"`.

</show>

### Cache Headers

A dynamic source with `staleTime`, in milliseconds, is read again once that time has passed. Its pages rendered on demand, with their `.md` file and Open Graph image, get `Cache-Control: public, s-maxage=<staleTime in seconds>`, so a CDN keeps them for the same time:

```tsx title="press.config.tsx"
createPress({ ...notion.dynamicSource(), staleTime: 60_000 });
```

Without `staleTime`, Fumapress sets no `Cache-Control`.

<show when={props.framework === "waku"}>

## Platforms

The adapter for Vercel, Netlify or Cloudflare is detected at build time. Other platforms get the Node.js adapter. When nothing [needs a server](#what-needs-a-server), the build has no function, like a Vercel Function, and the platform serves static files.

The platforms serve prerendered pages and the files of `public/` without your function, so middleware only runs for routes rendered on demand. On a Node.js server, it runs for every request.

### Node.js

```npm
npm run build
npm run start
```

To run the server without the CLI, like in a container:

```bash
PORT=8080 node dist/serve-node.js
```

### Vercel

Import the repository.

### Netlify

Import the repository. The build generates a `netlify.toml`, unless your project has one. Commit it, or copy its settings into yours.

<Callout type="warn">
  Keep Pretty URLs off in your own `netlify.toml`, so that pages keep their URLs without a trailing
  slash.
</Callout>

### Cloudflare

[Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/) is detected for you. To deploy from elsewhere, [set the adapter](#building-for-another-platform), build, then run:

```bash
npx wrangler deploy
```

Workers Builds doesn't expose the site URL, so set [`site.baseUrl`](./configuration.mdx#url).

The build generates a `wrangler.jsonc`, unless your project has a Wrangler config. In your own config, keep `html_handling: "drop-trailing-slash"`, and set `assets.directory` to `./dist/public` when nothing needs a server.

<Callout type="warn">
  Open Graph images rendered on demand can exceed the 10 ms of CPU time per request on the Workers
  Free plan.
</Callout>

### Building for Another Platform

To build for a platform outside of its own build system, like in your own CI, set `adapter`:

```ts title="vite.config.ts"
press({
  adapter: "waku/adapters/cloudflare",
});
```

## Static Hosts

For GitHub Pages, a CDN or any file host, the site must have [nothing that needs a server](#what-needs-a-server).

### Turn Off Image Optimization [step]

If you installed `sharp`, [turn off image optimization](./content.mdx#disabling-optimization).

### Upload the Build [step]

Build, then upload `dist/public`.

The build generates a `404.html`, which most hosts use automatically. With [internationalization](./internationalization.mdx), it is in the default language.

</show>

## Adapters

Add an [adapter](https://docs.astro.build/en/guides/on-demand-rendering) to render routes on demand. Pages of static sources stay prerendered.

```js title="astro.config.mjs"
export default defineConfig({
  site: "https://acme.dev",
  adapter: node({ mode: "standalone" }), // [!code ++]
  integrations: [press()],
});
```

<Callout type="warn">
  With the Node.js adapter, start the server with `NODE_ENV=production`. Without it, React runs its
  development build on the server.
</Callout>

```bash
NODE_ENV=production node dist/server/entry.mjs
```

### Rendering Every Page on Demand

With `output: "server"`, pages of static sources render on demand too, unless `mode` prerenders them. Use it when every page must run middleware, like [authentication](./authentication.mdx).

```js title="astro.config.mjs"
export default defineConfig({
  output: "server", // [!code ++]
  adapter: node({ mode: "standalone" }),
  integrations: [press()],
});
```

### Post-Build Plugins

Plugins like [link validation](./plugins/link-validation.mdx) read the pages that Astro prerenders during the build. A build that prerenders elsewhere, with `experimental.parallelPrerender` or an adapter prerendering outside of Node.js, fails and prints the reason.

Files written by these plugins go to your Astro `outDir`, which is public on a static host.

</show>

## Base Path

<show when={props.framework === "waku"}>

For a URL like `https://user.github.io/repo/`, set `basePath` and include the path in `site.baseUrl`. On Cloudflare, this needs Wrangler 4.148 or later.

```ts tab="vite.config.ts"
press({
  basePath: "/repo/",
});
```

```tsx tab="press.config.tsx"
createPress(content).config({
  site: {
    baseUrl: "https://user.github.io/repo",
  },
});
```

</show>

<show when={props.framework === "astro"}>

For a URL like `https://user.github.io/repo/`, set `site` and `base`:

```js title="astro.config.mjs"
export default defineConfig({
  site: "https://user.github.io",
  base: "/repo",
  integrations: [press()],
});
```

`page.url` and other loader paths don't include `base`, so use `withBase()` on [custom pages](./custom-pages.mdx#reading-content).

</show>
